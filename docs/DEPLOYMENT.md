# Поставка и обновление node-agent

## Окружения

Один OCI-образ используется в `develop` и `prod`: окружение не встраивается в
бинарный файл и задаётся только инфраструктурной конфигурацией. Каждое окружение
независимо закрепляет образ по `sha256` digest. Продвижение в `prod` повторно не
собирает образ, а использует digest, уже проверенный в `develop`.

Ветка одна — `main`. Каждый её commit публикует образ с тегом `sha-<git-sha>` и
попадает в среду `develop`. Релизный semver тег `vX.Y.Z` ставится на commit,
доступный из `main`; workflow добавляет тег к существующему manifest digest без
повторной сборки и проверяет, что digest при этом не изменился. Если образ
`sha-<git-sha>` отсутствует или commit недоступен из `main`, release завершается
ошибкой.

Промежуточной ветки нет намеренно. С ней релизный тег вставал бы на commit,
созданный слиянием, а такой commit никогда не собирался — продвижение не нашло бы
образ. Сохранить SHA при слиянии через интерфейс GitHub невозможно: merge, squash
и rebase создают новые SHA все три.

Тег `sha-<git-sha>` — единственный. Тег по имени ветки не публикуется: он был бы
пригоден для навигации по registry, но именно на него смотрело продвижение, и
переименование ветки тихо ломало бы release. Идентичность деплоя в любом случае
несёт digest, а не тег.

Образ публикуется в `ghcr.io/<organization>/node-agent` для `linux/amd64` и
`linux/arm64`, с provenance и SBOM. Точный `image@sha256:...` выводится в
GitHub Actions summary. Пакет GHCR требуется один раз переключить в публичный
режим в настройках организации.

## Передача инфраструктуре

Репозиторий не выкатывает агента и не знает, где стоят ноды. После публикации
образа workflow отправляет `repository_dispatch` с типом `agent-release` в
репозиторий инфраструктуры:

```json
{
  "environment": "develop | prod",
  "source_git_sha": "<40 hex>",
  "image": {"repository": "ghcr.io/<organization>/node-agent", "digest": "sha256:..."}
}
```

Это уведомление о факте, а не команда на выкатку. Принимающая сторона записывает
digest в свой desired state отдельным commit'ом и раскатывает уже его: версия,
работающая на нодах, обязана быть видна в Git, иначе следующий рутинный прогон
конвергенции вернул бы прежнюю и молча откатил среду.

Для `develop` этот путь проходит без участия человека. Для `prod` инфраструктура
останавливается на pull request.

Отправка требует секрета с правом записи в репозиторий инфраструктуры;
`GITHUB_TOKEN` для этого не подходит — его права ограничены своим репозиторием.

Финальный образ запускается без root от UID/GID `65532`. Каталог состояния,
который инфраструктура монтирует в `/var/lib/spirit-agent`, должен принадлежать
этому пользователю и иметь права `0700`.

Каталог, содержащий `/opt/vpn/xray/config.json`, также монтируется read-write и
разрешает UID/GID `65532` создание временного файла и атомарный rename. Bind
mount только самого файла не подходит: он не поддерживает атомарную замену.
Xray читает тот же файл при каждом старте.

## SQLite и rollback

Текущая версия агента принимает свою или более старую версию схемы SQLite и
отвергает более новую. Это намеренное fail-closed поведение: старый бинарный файл
не должен записывать данные в неизвестную ему схему.

Для обновлений действует простое правило:

1. Если release не добавляет SQL-миграцию, rollback на предыдущий образ разрешён.
2. Release с новой SQL-миграцией является rollback barrier, пока для конкретной
   миграции отдельно не доказана совместимость с предыдущим агентом.
3. Rollback barrier указывается в pull request и release notes.
4. До применения такой версии инфраструктура сохраняет согласованную резервную
   копию SQLite после штатной остановки агента.
5. Удаление SQLite не является способом rollback: база может содержать
   неподтверждённый usage outbox.

Отдельный общий механизм совместимости N−1 не вводится до появления миграции,
для которой он действительно потребуется.

## CI и уведомления

Основной CI проверяет тесты с детектором гонок, минимальное покрытие 80%,
`go vet`, protobuf и сборку бинарного файла. HTML-отчёт о покрытии сохраняется в
GitHub Actions artifacts, а отдельный workflow добавляет результат в pull
request.

Telegram-уведомления используют те же repository secrets, что и backend:

```text
TELEGRAM_BOT_TOKEN
TELEGRAM_CHAT_ID
```

Покрытие отправляется в topic `18`, события и ежедневная сводка pull request —
в topic `20`. Если secrets не настроены, workflow пропускает отправку.
